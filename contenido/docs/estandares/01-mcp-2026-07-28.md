La revisión **`2026-07-28`** de la especificación de [[glosario/mcp|MCP]] convierte el protocolo en **sin estado**. Desaparecen el saludo `initialize` y las sesiones de protocolo (`Mcp-Session-Id`). Cada petición viaja con su versión y sus capacidades, y cualquier réplica del servidor puede atenderla. Esta página explica qué cambia respecto a `2025-11-25` y cómo migrar. Si buscas qué es MCP, sus primitivas y cómo escribir un servidor, empieza por [[docs/herramientas/02-mcp]] y el curso [[cursos/mcp-de-cero-a-servidor/index]].

La fuente es el [changelog oficial de 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog). El código está probado con el SDK de Python `mcp` 2.3.0.

## Por qué sin estado

Las sesiones nunca tuvieron un significado común. El documento de diseño que las elimina ([SEP-2567](https://modelcontextprotocol.io/seps/2567-sessionless-mcp.md)) recoge que unos clientes abrían una sesión por llamada a herramienta, otros una por arranque de la aplicación y casi ninguno las reanudaba. Un servidor que guardaba estado «en la sesión» no sabía cuánto iba a durar ese estado. Además, como `tools/list` podía variar por sesión, el cliente tenía que volver a pedirlo en cada sesión nueva, también cada subagente.

Sin sesiones pasan tres cosas útiles:

- **Escalas detrás de un balanceador normal**, sin afinidad de sesión (*sticky sessions*).
- **Las listas se pueden cachear** por servidor, no por conexión.
- **El estado que necesites se vuelve explícito**: un identificador que crea el servidor y que el modelo pasa como argumento.

## Qué cambia en el núcleo

| Antes (≤ 2025-11-25) | Ahora (2026-07-28) |
|---|---|
| `initialize` + `notifications/initialized` al conectar | Nada: cada petición lleva versión, capacidades e identidad del cliente en `_meta` |
| Cabecera `Mcp-Session-Id` | Eliminada; el estado entre llamadas va en *handles* |
| Capacidades negociadas una vez | `server/discover` (obligatorio en el servidor) anuncia versiones, capacidades e identidad |
| El servidor envía peticiones al cliente (`elicitation/create`, `sampling/createMessage`, `roots/list`) | **MRTR**: el servidor responde `input_required` y el cliente reintenta con las respuestas |
| GET HTTP y `resources/subscribe` | `subscriptions/listen`: un único flujo para los avisos de cambios |
| `ping`, `logging/setLevel` | Eliminados; el nivel de log va por petición (`io.modelcontextprotocol/logLevel` en `_meta`) |
| Reanudación SSE con `Last-Event-ID` | Eliminada: si se corta el flujo, el cliente reenvía la petición con otro `id` |
| Tasks en el núcleo (experimental) | Extensión `io.modelcontextprotocol/tasks` ([[docs/estandares/02-extensiones-mcp]]) |

Otros cambios menores que te afectan al escribir un servidor:

- Todos los resultados llevan **`resultType`**: `"complete"` o `"input_required"`. Si un servidor antiguo no lo envía, el cliente lo trata como `"complete"`.
- Las respuestas de `tools/list`, `prompts/list`, `resources/list`, `resources/read` y `resources/templates/list` llevan **`ttlMs`** (cuánto tiempo, en milisegundos, se puede considerar fresco el resultado) y **`cacheScope`** (`"public"` si un intermediario lo puede compartir entre usuarios, `"private"` si no).
- `tools/list` **debería** devolver las herramientas en **orden determinista**. Así el cliente cachea mejor y el prefijo del prompt no cambia entre llamadas, lo que ayuda al [[docs/contexto/02-prompt-caching|prompt caching]].
- En Streamable HTTP, las peticiones POST llevan las cabeceras `Mcp-Method` y `Mcp-Name`, para que un *proxy* enrute sin abrir el cuerpo.
- `inputSchema` y `outputSchema` admiten cualquier palabra clave de JSON Schema 2020-12.

## Una petición por dentro

Así viaja ahora una llamada a herramienta. No hay saludo previo: la versión y las capacidades van en el propio mensaje.

```json title="tools/call en 2026-07-28"
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "anadir",
    "arguments": {"cesta_id": "cst_4TrBgMpPzmPOzASQk6umcg", "sku": "cafe-250g"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {"elicitation": {}},
      "io.modelcontextprotocol/clientInfo": {"name": "mi-agente", "version": "0.3.0"}
    }
  }
}
```

Si el servidor no soporta esa versión, responde con `UnsupportedProtocolVersionError` y la lista de versiones que sí admite. El cliente puede llamar antes a `server/discover` para elegir versión, aunque no está obligado. En `stdio`, un cliente que quiera hablar con servidores nuevos y antiguos puede usar `server/discover` como sonda: si falla, vuelve al saludo `initialize`. El `Client` del SDK de Python hace exactamente eso en su modo por defecto (`mode="auto"`).

```json title="Respuesta de server/discover (real, del ejemplo de abajo)"
{
  "resultType": "complete",
  "supportedVersions": ["2026-07-28"],
  "capabilities": {"tools": {"listChanged": true}, "resources": {"subscribe": true, "listChanged": true}, "prompts": {"listChanged": true}},
  "instructions": "Crea una cesta con crear_cesta y pasa su cesta_id a las demás herramientas.",
  "_meta": {"io.modelcontextprotocol/serverInfo": {"name": "tienda", "version": ""}},
  "ttlMs": 0,
  "cacheScope": "private"
}
```

`serverInfo` lo declara el propio servidor y nadie lo verifica: úsalo para mostrar y registrar, nunca para decisiones de seguridad.

## MRTR: pedir datos sin guardar estado

Antes, un servidor que necesitaba confirmación de la persona enviaba una petición `elicitation/create` al cliente en mitad de la llamada y esperaba la respuesta con la conexión abierta. Eso exige que la misma réplica reciba la respuesta. Con [[glosario/mrtr|MRTR]] (*Multi Round-Trip Requests*) el servidor **termina** la petición con un resultado intermedio:

1. El cliente llama a `tools/call`.
2. El servidor responde `resultType: "input_required"` con `inputRequests` (un mapa de preguntas: elicitación, *sampling* o *roots*) y, si lo necesita, un `requestState` opaco.
3. El cliente reúne las respuestas y **reintenta la misma petición** con otro `id`, añadiendo `inputResponses` y el `requestState` tal cual.
4. El servidor reconstruye el contexto a partir del reintento y devuelve el resultado.

Solo `tools/call`, `prompts/get` y `resources/read` pueden devolver `input_required`. El servidor tampoco puede pedir algo que el cliente no haya declarado en sus capacidades (sin `elicitation`, no hay preguntas de formulario).

> [!peligro] `requestState` pasa por el cliente
> La especificación obliga a tratarlo como **entrada controlada por un atacante**. Si influye en permisos o en lógica de negocio, protégelo con HMAC o AEAD y rechaza el que no verifique. Incluye dentro el usuario autenticado, una caducidad corta y la petición de origen para evitar que se reutilice. El SDK de Python lo sella con AES-256-GCM. Por defecto usa una clave efímera del proceso: con varias réplicas, comparte la clave con `MCPServer(..., request_state_security=RequestStateSecurity(keys=[clave]))`.

## Migrar un servidor con estado a handles

El patrón que propone la especificación no es una construcción nueva del protocolo. Es diseño de herramientas: una herramienta `crear_*` devuelve un identificador y las demás lo reciben como argumento. El ejemplo clásico es una cesta de la compra.

```diff title="Antes y después"
- @mcp.tool()
- def anadir(sku: str, ctx: Context) -> str:
-     CESTAS[id_de_sesion(ctx)].append(sku)   # estado escondido en la sesión
+ @mcp.tool()
+ def crear_cesta() -> Cesta: ...            # devuelve cesta_id
+ @mcp.tool()
+ def anadir(cesta_id: str, sku: str) -> Cesta: ...
```

El servidor completo, con el *handle*, una pista de caché para `tools/list` y una confirmación por MRTR antes de vaciar la cesta. Se prueba en proceso con `mcp.Client`, sin red:

```python title="tienda.py"
import asyncio
import secrets
import time
from typing import Annotated

from pydantic import BaseModel

from mcp import Client
from mcp.server import CacheHint
from mcp.server.mcpserver import Elicit, MCPServer, Resolve
from mcp.server.mcpserver.exceptions import ToolError
from mcp.types import ElicitResult

DURACION_S = 24 * 3600  # una cesta caduca tras 24 h sin uso

mcp = MCPServer(
    "tienda",
    instructions="Crea una cesta con crear_cesta y pasa su cesta_id a las demás herramientas.",
    cache_hints={"tools/list": CacheHint(ttl_ms=3_600_000, scope="public")},
)

CESTAS: dict[str, dict] = {}  # en producción: Redis o tu base de datos, compartida por las réplicas


class Cesta(BaseModel):
    cesta_id: str
    lineas: dict[str, int]


def _cesta(cesta_id: str) -> dict:
    c = CESTAS.get(cesta_id)
    if c is None or time.time() - c["tocada"] > DURACION_S:
        raise ToolError(f"La cesta {cesta_id} no existe o ha caducado. Crea otra con crear_cesta.")
    c["tocada"] = time.time()
    return c


@mcp.tool()
def crear_cesta() -> Cesta:
    """Crea una cesta vacía y devuelve su cesta_id. Las cestas caducan tras 24 h sin uso."""
    cesta_id = "cst_" + secrets.token_urlsafe(16)  # opaco y con 128 bits de entropía
    CESTAS[cesta_id] = {"lineas": {}, "tocada": time.time()}
    return Cesta(cesta_id=cesta_id, lineas={})


@mcp.tool()
def anadir(cesta_id: str, sku: str, unidades: int = 1) -> Cesta:
    """Añade unidades de un producto (sku) a la cesta indicada."""
    lineas = _cesta(cesta_id)["lineas"]
    lineas[sku] = lineas.get(sku, 0) + unidades
    return Cesta(cesta_id=cesta_id, lineas=lineas)


class Confirmacion(BaseModel):
    confirmar: bool


def pedir_confirmacion(cesta_id: str) -> Elicit[Confirmacion]:
    return Elicit(f"¿Vaciar la cesta {cesta_id}?", Confirmacion)


@mcp.tool()
def vaciar(cesta_id: str, ok: Annotated[Confirmacion, Resolve(pedir_confirmacion)]) -> str:
    """Vacía la cesta. Pide confirmación a la persona antes de hacerlo."""
    if not ok.confirmar:
        return "No se ha vaciado la cesta."
    _cesta(cesta_id)["lineas"].clear()
    return f"Cesta {cesta_id} vaciada."


async def responder(contexto, params) -> ElicitResult:
    print("  el servidor pregunta:", params.message)  # aquí tu host preguntaría a la persona
    return ElicitResult(action="accept", content={"confirmar": True})


async def main() -> None:
    async with Client(mcp, elicitation_callback=responder) as c:
        print("versión:", c.protocol_version)
        lista = await c.list_tools()
        print("ttl_ms:", lista.ttl_ms, "| scope:", lista.cache_scope)

        cesta_id = (await c.call_tool("crear_cesta", {})).structured_content["cesta_id"]
        r = await c.call_tool("anadir", {"cesta_id": cesta_id, "sku": "cafe-250g", "unidades": 2})
        print("tras añadir:", r.structured_content["lineas"])

        primera = await c.session.call_tool("vaciar", {"cesta_id": cesta_id}, allow_input_required=True)
        print("resultType:", primera.result_type)  # lo que ve un cliente que lleva el bucle a mano

        r = await c.call_tool("vaciar", {"cesta_id": cesta_id})  # Client reintenta solo
        print("vaciar:", r.content[0].text)

        r = await c.call_tool("anadir", {"cesta_id": "cst_inventado", "sku": "te"})
        print("handle malo:", r.is_error, r.content[0].text)


if __name__ == "__main__":
    asyncio.run(main())
```

```text
versión: 2026-07-28
ttl_ms: 3600000 | scope: public
tras añadir: {'cafe-250g': 2}
resultType: input_required
  el servidor pregunta: ¿Vaciar la cesta cst_4TrBgMpPzmPOzASQk6umcg?
vaciar: Cesta cst_4TrBgMpPzmPOzASQk6umcg vaciada.
handle malo: True Error executing tool anadir: La cesta cst_inventado no existe o ha caducado. Crea otra con crear_cesta.
```

Qué hace cada pieza:

- **`Resolve(pedir_confirmacion)`** rellena el parámetro `ok` antes de ejecutar la herramienta. Si el resolvedor devuelve `Elicit(...)`, el SDK responde `input_required` con la pregunta en `inputRequests` y el contexto sellado en `requestState`. Con un cliente antiguo (`2025-11-25`), el mismo código envía la elicitación clásica a mitad de la llamada.
- **`elicitation_callback`** es la parte del cliente: el `Client` detecta `input_required`, llama al *callback* y reintenta, hasta `input_required_max_rounds` vueltas (10 por defecto).
- **`cache_hints`** rellena `ttlMs` y `cacheScope` de las listas. Pon `public` solo si la lista es igual para todos los usuarios.
- El mismo servidor atiende también a clientes antiguos: con `Client(mcp, mode="legacy")` la conexión negocia `2025-11-25` mediante `initialize`.

La receta [[recetas/servidor-mcp-sin-estado-con-handles]] lleva este patrón a un servidor HTTP con varias réplicas y almacén compartido.

## Buenas prácticas con handles

Las recoge el propio SEP-2567, y no son normativas:

| Práctica | Por qué |
|---|---|
| Identificadores **opacos** (`cst_a1b2…`), nunca `cesta_usuario42` | Un formato legible invita al modelo a adivinarlo o construirlo |
| **Tener el handle no da permiso** | Valida `(handle, usuario autenticado)` en cada llamada; el handle acabará en registros y prompts de subagentes |
| Sin autenticación, **128 bits de entropía** y vida limitada | El handle es entonces un token al portador |
| **La caducidad, en la descripción** de `crear_*` | El modelo la lee al decidir crear estado; la documentación del servidor no la ve |
| **Errores de caducidad claros** («la cesta ha caducado, crea otra») | El modelo se recupera llamando de nuevo a `crear_*` |
| Parámetros en la creación (`crear_contexto(cluster="staging")`) | Una llamada en lugar de dos y nada a medio configurar |
| Herramientas `destruir_*` y `listar_*` opcionales | Liberar recursos y recuperar lo perdido tras una [[glosario/compactacion|compactación]] |

Una consecuencia menos obvia: **las listas ya no pueden cambiar como efecto de otra llamada**. El patrón «llamar a `conectar_bd` hace aparecer `consultar` en `tools/list`» deja de ser válido. Expón `consultar` desde el principio con un argumento `conexion_id` y devuelve un error claro si falta.

## Deprecaciones y plazos

La revisión adopta una [política de ciclo de vida](https://modelcontextprotocol.io/community/feature-lifecycle.md) con tres estados (Active, Deprecated, Removed). Una función deprecada sigue en la especificación al menos **doce meses** contados desde la publicación de la revisión que la deprecó. Solo un riesgo de seguridad activo permite acortarlo, y nunca por debajo de noventa días. Los SDK de *tier* 1 deben marcar la API deprecada y deberían avisar en tiempo de ejecución.

| Deprecado en 2026-07-28 | Alternativa que propone la especificación |
|---|---|
| *Roots* | Pasa carpetas o archivos como parámetros de herramienta, URIs de recurso o configuración del servidor |
| *Sampling* | Llama directamente a la API del proveedor del modelo |
| *Logging* | `stderr` (en `stdio`) u OpenTelemetry |
| Transporte HTTP+SSE | Streamable HTTP |
| `includeContext` `thisServer` y `allServers` | Omite el campo o usa `"none"` |
| Registro dinámico de clientes OAuth (DCR) | *Client ID Metadata Documents* (CIMD) |

En autorización hay además tres cambios: validar el parámetro `iss` de la respuesta de autorización (RFC 9207), indicar `application_type` al registrarse y ligar las credenciales guardadas al servidor de autorización que las emitió. Los detalles de despliegue están en [[cursos/mcp-de-cero-a-servidor/04-seguridad-y-despliegue]].

## Errores frecuentes al migrar

- **Guardar estado en memoria del proceso y desplegar varias réplicas.** Funciona en local con `stdio` y falla en cuanto el balanceador reparte peticiones. El estado va a un almacén compartido, indexado por el *handle*.
- **No compartir la clave de `requestState`** entre réplicas: el reintento de MRTR llega a otra réplica y se rechaza.
- **Marcar `cacheScope: "public"`** en listas que dependen del usuario.
- **Seguir llamando a `ctx.log()`**: el SDK lo marca como deprecado. Escribe en `stderr` o en tus trazas.
- **Confiar en que el cliente reintente.** La especificación no lo garantiza: un `input_required` sin respuesta no debe dejar nada a medias.
